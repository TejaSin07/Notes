3) What is the use of @Repository annotation? : convert db exception to java exception

Scenario:
- We have an Entity class User with an email field.
- Email column is marked as UNIQUE.
- JPA creates a database table with a UNIQUE constraint on email.

Flow when duplicate email is saved:

1. Client sends a request with an email that already exists in the database.

2. Service layer calls the repository method:
   userRepository.save(user);

3. The repository is actually a Spring-generated PROXY,
   not the real implementation.

4. The proxy delegates the call to:
   Proxy → EntityManager → Hibernate → JDBC → Database

5. Database detects UNIQUE constraint violation and throws
   a checked JDBC exception:
   - SQLException / SQLIntegrityConstraintViolationException

6. Hibernate catches this checked exception and WRAPS it into
   an unchecked runtime exception:
   - ConstraintViolationException
   - PersistenceException

7. Because the class is annotated with @Repository,
   Spring applies PersistenceExceptionTranslationInterceptor.

8. Spring intercepts the runtime persistence exception and
   TRANSLATES it into a database-independent unchecked exception:
   - DataIntegrityViolationException

9. This unchecked exception is thrown to the service layer.
   - No throws declaration required
   - No database-specific exception leakage

10. Spring marks the transaction for rollback and the normal
    execution flow stops.

Conclusion:
- @Repository enables automatic exception translation.
- It converts low-level, vendor-specific persistence exceptions
  into Spring’s unified DataAccessException hierarchy.
- This keeps service layer clean and database-independent.

JDBC (checked)
   ↓
Hibernate/JPA (unchecked, ORM-specific)
   ↓
Spring (@Repository) (unchecked, generic)

Exception translation means JDBC throws checked exceptions, JPA/Hibernate converts them into unchecked persistence exceptions, and Spring further translates them into generic, database-independent unchecked DataAccessExceptions

5) if we can write findBy then why specification??

findBy methods create static queries with mandatory parameters, whereas Specifications allow building dynamic queries that handle optional values and complex business logic in a single reusable method.

When we want a single logical method that can handle all filtering logic based on business rules, we use Specification.

Why?
Using findBy :: 
Each findBy method has fixed conditions
All parameters are mandatory
Cannot skip a condition
For different combinations, we must:
Write multiple findBy methods, or
Write one very long findBy with all conditions
Becomes hard to maintain

Using Specification ::
We can write one method
Filters are added dynamically

Conditions can be:
Added only when value is present
Skipped when value is null

Handles:
AND / OR
, <, BETWEEN
Complex business rules
Perfect for UI-driven search and business logic

ex specification ::

Specification<Employee> spec = (root, query, cb) -> {

    List<Predicate> predicates = new ArrayList<>();

    if (name != null) {
        predicates.add(cb.equal(root.get("name"), name));
    }

    if (minSalary != null) {
        predicates.add(cb.greaterThanOrEqualTo(
                root.get("salary"), minSalary));
    }

    if (maxSalary != null) {
        predicates.add(cb.lessThanOrEqualTo(
                root.get("salary"), maxSalary));
    }

    if (department != null) {
        predicates.add(cb.equal(root.get("department"), department));
    }

    if (status != null) {
        predicates.add(cb.equal(root.get("status"), status));
    }

    return cb.and(predicates.toArray(new Predicate[0]));
};

6) Why uuid if we have primary key?
- When we share UUID instead of the primary key, the user cannot guess or predict the next identifier.
- Numeric primary keys (IDENTITY) are sequential, so a user can easily assume the next or previous ID.
- Predictable IDs can allow users to access or perform actions on data that should not be exposed (ID enumeration).
- UUIDs are random and non-sequential, so the next UUID cannot be predicted.

7) what's the diff in Identity and sequence
SEQUENCE:
- Sequence generates the next ID value BEFORE inserting the record.
- Hibernate fetches the next ID(s) using SELECT NEXTVAL.
- IDs are assigned in memory first.
- Data is then inserted along with the IDs.
- Because IDs are already known, multiple records can be inserted in a batch.

Example:
SELECT emp_seq.NEXTVAL;   --> returns 100
INSERT INTO emp(id, name) VALUES (100, 'A');
INSERT INTO emp(id, name) VALUES (101, 'B');

IDENTITY:
- ID is generated by the database DURING the insert.
- Data is inserted first without an ID.
- Database generates the ID and places it in the primary key column.
- Hibernate must wait for the ID after each insert.
- Because IDs are generated one by one, batch insert is NOT possible.

Example:
INSERT INTO emp(name) VALUES ('A');  --> DB generates id = 1
INSERT INTO emp(name) VALUES ('B');  --> DB generates id = 2

Conclusion:
SEQUENCE knows IDs before insert → batch insert possible.
IDENTITY gets IDs after insert → batch insert not possible.


With IDENTITY, the database generates the primary key only after each row is inserted, and JDBC can return generated keys only one row at a time.
Because Hibernate must map each Java entity to its generated ID, it is forced to insert rows one by one.

12) PUT vs PATCH – Conclusion

=> There is NO inbuilt PUT or PATCH method in CrudRepository/JpaRepository.
   Repositories only provide save(), findById(), delete().

=> PUT is used for FULL replacement of a resource.
   → Client sends complete JSON.
   → Service layer overwrites all fields (no null checks).

=> PATCH is used for PARTIAL update of a resource.
   → Client sends only changed fields.
   → Service layer updates only non-null fields.

=> save() [insert + update] does not know PUT or PATCH semantics.
   → It simply persists the current entity state.

=> PUT/PATCH behavior is implemented in the SERVICE layer,
   not in the repos

Q. Why private method cannot intercepts by aop?
=> AOP works by creating a proxy (often by subclassing the target class).
Private methods cannot be inherited or overridden, so the proxy cannot intercept them.

| AOP Advice        | Java Equivalent   | Runs on Exception?   |
| ----------------- | ----------------- | ------------------   |
| `@Before`         | code before `try` | ✅ Yes              |
| `@AfterReturning` | after success     | ❌ No               |
| `@AfterThrowing`  | `catch` block     | ✅ Yes              |
| `@After`          | `finally` block   | ✅ Yes              |

1️⃣ What does execution(...) mean in AOP?

- execution is a pointcut designator.
- It tells Spring WHERE your aspect should run.
- It intercepts METHOD EXECUTION that matches a given pattern.

General syntax:

execution(
    return-type
    package.class.method(arguments)
)

Example used:

execution(* in.tejas.service.*.*(..))

✔  Classes directly inside in.tejas.service
✔  Any method in those classes
❌ Does NOT match sub-packages inside service


Breakdown:

*                    		-> any return type
in.tejas.service     		-> package name
*                    		-> any class
*                    		-> any method
(..)                		-> any number of arguments

Result:
- Aspect runs for every method in every class inside in.tejas.service package

2️⃣ Why execution is MOST USED in Spring AOP

Spring AOP is:
- method-level
- proxy-based

So Spring AOP can intercept:
✔️ method execution

But it CANNOT intercept:
❌ field access
❌ constructor calls (in Spring AOP)

That’s why execution() is the most commonly used pointcut.

3️⃣ Other important execution patterns (REAL USE CASES)

// Specific method
execution(* in.tejas.service.UserService.createUser(..))

// Specific return type
execution(String in.tejas.service.*.*(..))

// Specific argument
execution(* in.tejas.service.*.*(String))

// Multiple arguments
execution(* in.tejas.service.*.*(String, Integer))

// Methods starting with "get"
execution(* in.tejas.service.*.get*(..))


4️⃣ Other pointcut designators (VERY IMPORTANT)
Spring AOP supports more than just execution().

// 1️⃣ within
// Match by class or package
within(in.tejas.service..*)
// Matches all classes under service package (including sub-packages)


// 2️⃣ @annotation
// Match methods having a specific annotation (MOST POWERFUL)
@annotation(in.tejas.annotation.LogExecutionTime)

// Used heavily in real projects
// Clean, readable, and precise


// 3️⃣ @within
// Match classes annotated with a specific annotation here it is @Service
@within(org.springframework.stereotype.Service)


// 4️⃣ args
//Match any method execution where the runtime argument list contains exactly 
one argument of type String.
args(String)


// 5️⃣ bean
// Match by Spring bean name
bean(userService)
@Service
public class UserService {
    public void create() {}
}


5️⃣ What Spring AOP CANNOT do (VERY IMPORTANT)

Because Spring AOP is proxy-based:
❌ Constructor interception (coz call happen only after obj creation)
❌ Field access
❌ Private methods
❌ Internal method calls (this.method())

For these use cases, we need:
- AspectJ (compile-time or load-time weaving)
*/

Instead of repeating pointcut expressions everywhere like:

----------------------Self Created annotation------------------

*****************************************************************
  STEP 1: CREATE A CUSTOM ANNOTATION
 *****************************************************************

/*
 * @interface tells Java: this is an annotation type (not a class, not an interface)
 */
@Retention(RetentionPolicy.RUNTIME) 
// RUNTIME => annotation will be available at JVM runtime
// REQUIRED for Spring, AOP, Reflection

@Target(ElementType.METHOD) 
// METHOD => annotation can be applied only on methods

public @interface LogExecution {

    /*
     * Annotation attributes look like methods
     * They do NOT have method bodies
     */

    String value() default "";
    // Optional description

    boolean enabled() default true;
    // Flag to enable / disable logic
}


/*****************************************************************
 * STEP 2: USE THE ANNOTATION
 *****************************************************************/

@Service
public class UserService {

    @LogExecution(value = "Create User Logic", enabled = true)
    public void createUser() {
        System.out.println("Creating user...");
    }

    /*
     * IMPORTANT:
     * - Annotation alone does NOTHING
     * - No logic runs here automatically
     */
}



/*****************************************************************
 * STEP 3: CREATE ASPECT (THIS IS WHERE LOGIC LIVES)
 *****************************************************************/

@Aspect
@Component
public class LogExecutionAspect {

    /*
     * @Around => execute logic before + after method
     *
     * @annotation(logExecution)
     * - Match methods annotated with @LogExecution
     * - Spring injects annotation instance into advice
     */
    @Around("@annotation(logExecution)")
    public Object execute(
            ProceedingJoinPoint joinPoint,
            LogExecution logExecution
    ) throws Throwable {

        // Check annotation flag
        if (!logExecution.enabled()) {
            return joinPoint.proceed();
        }

        long startTime = System.currentTimeMillis();

        // Call actual method
        Object result = joinPoint.proceed();

        long endTime = System.currentTimeMillis();

        System.out.println(
            logExecution.value() +
            " executed in " +
            (endTime - startTime) + " ms"
        );

        return result;
    }
}


/*****************************************************************
 * STEP 4: WHAT HAPPENS INTERNALLY (RUNTIME FLOW)
 *****************************************************************/

/*
1. Spring starts application
2. Spring scans beans
3. Finds @Aspect class
4. Creates PROXY for UserService
5. Client calls createUser()
6. Call goes to PROXY (not real object)
7. Proxy checks pointcut
8. @LogExecution found
9. Aspect logic executes
10. Real method is invoked
11. Aspect runs after logic
12. Result returned
*/


/*****************************************************************
 * STEP 5: WHY @Retention(RUNTIME) IS MANDATORY
 *****************************************************************/

/*
“Retention specifies how long an annotation is available (source, class, or runtime), while Target specifies where the annotation can be applied, such as method, class, or field.”


If you use:
@Retention(RetentionPolicy.SOURCE)
-> Annotation exists only in source code
-> JVM cannot see it
-> Spring cannot read it

If you use:
@Retention(RetentionPolicy.CLASS)
-> Annotation in .class file
-> JVM does NOT expose it via reflection

ONLY THIS WORKS FOR SPRING:
@Retention(RetentionPolicy.RUNTIME)
*/


/*******************************************
 * STEP 6: IMPORTANT LIMITATIONS (MUST KNOW)
 *******************************************/

/*
❌ Annotation on private methods -> AOP WILL NOT WORK
❌ Self-invocation -> AOP WILL NOT WORK
❌ Annotation without Aspect -> DOES NOTHING

Reason:
Spring AOP works via PROXY
Proxy intercepts only external public method calls
*/


/*****************************************************************
 * STEP 7: INTERVIEW-READY SUMMARY (IN COMMENTS)
 *****************************************************************/

/*
Custom annotations are metadata created using @interface.
They are controlled by @Retention and @Target.
Annotations do not execute logic by themselves.
Frameworks like Spring read annotations using reflection or AOP.
In Spring AOP, proxies intercept method calls and apply logic
defined in aspects based on annotation presence.
*/

18) maven repo flow::

MAVEN DEPENDENCY RESOLUTION FLOW
--------------------------------

1) When we add a dependency in pom.xml:

   <dependency>
       <groupId>org.springframework.boot</groupId>
       <artifactId>spring-boot-starter-web</artifactId>
       <version>3.2.0</version>
   </dependency>

   Maven starts the dependency resolution process during build.

------------------------------------------------------------

2) Step 1 – Check Local Repository

   Location:
   ~/.m2/repository

   - Maven first checks whether the required artifact (JAR + POM) 
     already exists in the local repository.
   - If found → it uses the local copy.
   - No remote call is made.

------------------------------------------------------------

3) Step 2 – If NOT found locally

   Maven connects to a Remote Repository.

   The remote repository can be:

   a) Maven Central (default)
   b) Company Repository Manager (if configured)
      - Nexus
      - Artifactory

   Remote repository used depends on configuration.

------------------------------------------------------------

4) If NO company repository is configured:

   Flow:
   Local → Maven Central → Download → Store in Local

------------------------------------------------------------

5) If company repository (Nexus/Artifactory) is configured:

   Usually configured in:
   - settings.xml (recommended approach)
   - or pom.xml (less common in enterprise)

   Flow:
   Local → Nexus → (if not cached) → Maven Central
          → Nexus Cache → Local

   Nexus acts as:
   - Proxy for external dependencies
   - Host for internal company artifacts
   - Caching layer
   - Access control layer

------------------------------------------------------------

6) First-Time Download Behavior

   - Artifact is downloaded from remote repository.
   - Stored inside local repository (~/.m2).
   - Also cached in Nexus (if used).

------------------------------------------------------------

7) Subsequent Builds

   - Maven finds artifact in local repository.
   - No need to contact remote repository again.
   - Build becomes faster.

------------------------------------------------------------

8) Important Technical Clarifications

   - Maven always checks Local Repository first.
   - Maven Central is used by default if no mirror/repository is configured.
   - Nexus/Artifactory is NOT mandatory.
   - Nexus comes into the picture only if:
       * Configured via settings.xml (mirror)
       * Defined in pom.xml
       * Enforced by corporate build system

------------------------------------------------------------

9) Complete Resolution Order (Simplified)

   1. Local Repository
   2. Remote Repository (Nexus if configured)
   3. Maven Central (if allowed)

------------------------------------------------------------

10) Key Enterprise Understanding

   - Small projects → Directly use Maven Central.
   - Large enterprises → Use Nexus/Artifactory to:
       * Block direct internet access
       * Manage internal libraries
       * Cache external artifacts
       * Control dependency versions
       * Improve build stability

------------------------------------------------------------

Conclusion:

Maven dependency resolution is hierarchical:
Local first → then Remote (Nexus or Central).

Nexus is optional and only participates when explicitly configured.

================ MAVEN: PLUGIN vs DEPENDENCY =================

-----------------------------------------
PLUGIN  (Example: maven-surefire-plugin)
-----------------------------------------

Purpose:
- Used by Maven during build lifecycle.
- Controls execution of build phases.

Example:
- maven-surefire-plugin → Runs unit tests in "test" phase.

What Plugin Does:
- Does NOT add libraries to your application.
- Does NOT affect application runtime logic.
- Controls build execution (compile, test, package, deploy).
- Executes specific goals during lifecycle phases.

If Plugin Is Missing:
- Basic Maven build may still work (default lifecycle bindings).
- Unit tests may not run properly or advanced configuration won't work.
- Customization (parallel tests, includes/excludes) will fail.
- Enterprise build features may break.

---------------------------------------------------------------
DEPENDENCY  (Example: spring-boot-starter-web)
---------------------------------------------------------------

Purpose:
- Provides external libraries required by the application.

How Dependencies Work:
- Maven downloads required JAR files from repository.
- JARs are stored in local repository (~/.m2).
- Added to project class path.
- Available during compile and/or runtime (based on scope).

What Dependency Does:
- Adds external library code to your project.
- Allows your application to use classes and APIs.
- Affects application compile-time and runtime behavior.

If Dependency Is Missing:
- Compilation errors (class not found).
- Runtime failures (ClassNotFoundException).
- Application functionality breaks.

---------------------------------------------------------------
Core Difference:
Plugin  → Used by Maven to build the project.
Dependency → Used by Application to run the project.
---------------------------------------------------------------

1) What is Data Migration?
--------------------------
Data migration = Moving or transforming existing data 
when schema changes OR system changes.

Examples:
- Adding NOT NULL column with default value
- Splitting one column into two
- Moving data from old table to new table
- Changing datatype (INT → BIGINT)
- Renaming table with data preservation


2) Types of Migrations
----------------------

A) Schema Migration
   - Structure change
   - CREATE / ALTER / DROP
   - Handled via Flyway versioned SQL

B) Data Migration
   - Modifies existing data
   - UPDATE / INSERT INTO ... SELECT

CIRCULAR DEPENDENCY
===================

CIRCULAR DEPENDENCY (SPRING / JAVA)

Definition
Circular dependency occurs when two or more beans depend on each other directly or indirectly, 
creating a loop during bean creation.

Example:
A → B
B → A


1) WHY WE GET THIS PROBLEM

This problem occurs when two services/classes require each other during object creation.

Spring cannot decide which bean to create first.

Common causes:
- Poor service design
- Business logic spread across multiple services
- Tight coupling between components

Example:

@Service
class A {
    private B b;

    public A(B b){
        this.b = b;
    }
}

@Service
class B {
    private A a;

    public B(A a){
        this.a = a;
    }
}

Flow:

Spring tries to create A
A requires B
Spring tries to create B
B requires A

Result:
BeanCurrentlyInCreationException


2) HOW WE AVOID USING @Lazy

@Lazy delays bean creation until it is actually used.

Spring injects a proxy object instead of the real bean.

Example:

@Service
class A {

    private B b;

    public A(@Lazy B b){
        this.b = b;
    }
}

@Service
class B {

    private A a;

    public B(A a){
        this.a = a;
    }
}

Flow:

Create A
Inject proxy of B
Create B
Inject A

When A calls B method → real B is created.


3) HOW WE AVOID THIS USING SETTER INJECTION

Setter injection allows Spring to create objects first and inject dependencies later.

Example:

@Service
class A {

    private B b;

    @Autowired
    public void setB(B b){
        this.b = b;
    }
}

@Service
class B {

    private A a;

    @Autowired
    public void setA(A a){
        this.a = a;
    }
}

Flow:

Step 1: Create A object
Step 2: Create B object
Step 3: Inject B into A
Step 4: Inject A into B

Both beans are created successfully.

4) MORE REAL PROJECT EXAMPLES

Example 1

OrderService   → PaymentService
PaymentService → OrderService

Problem:
Order needs payment status
Payment needs order details


Example 2

UserService → RoleService
RoleService → UserService

Problem:
User needs role
Role service checks user


Example 3

AuditService → FindingService
FindingService → AuditService

Problem:
Audit creates findings
Finding validates audit


Best Solution (Recommended)

Introduce third service:

A → C
B → C

Example:

OrderPaymentHelper

Circular dependency occurs when two or more beans depend on each other, creating a loop during bean creation. It can be resolved using @Lazy, setter injection, or by redesigning services to remove tight coupling.

“IMP: we can introduce a third service to break circular dependency by extracting shared logic, but the real goal is to redesign dependencies to be unidirectional rather than just adding another class.”


MYSQL INDEXING NOTES
====================

1. CLUSTERED INDEX (InnoDB)

Definition
----------
Clustered index determines how the table data is physically stored.

In MySQL InnoDB:
PRIMARY KEY itself becomes the CLUSTERED INDEX.

Important Points
----------------
- Only ONE clustered index per table
- Data rows are physically stored in primary key order
- Clustered index contains the FULL ROW DATA
- Implemented using B+ Tree structure

Example
-------

CREATE TABLE employee (
    id INT PRIMARY KEY,
    name VARCHAR(50),
    salary INT
);

Inserted Data
-------------
id | name  | salary
3  | Rahul | 50000
1  | Amit  | 70000
5  | Neha  | 60000

Internally Stored (Clustered Order)
-----------------------------------
id | name  | salary
1  | Amit  | 70000
3  | Rahul | 50000
5  | Neha  | 60000

Explanation
-----------
The data is physically stored sorted by the PRIMARY KEY.


------------------------------------------------------------


2. NON-CLUSTERED INDEX (SECONDARY INDEX)

Definition
----------
Any index other than the primary key in MySQL is called a
SECONDARY INDEX (non-clustered index).

It does NOT store full rows.

Instead it stores:
    Indexed column value
    +
    Primary key value

MySQL then uses the primary key to fetch the actual row.


Example
-------

CREATE INDEX idx_salary
ON employee(salary);


Secondary Index Structure
-------------------------

salary | primary_key
40000  | 2
50000  | 3
60000  | 5
70000  | 1


Query
-----

SELECT * FROM employee WHERE salary = 60000;

Execution Steps
---------------

Step 1
MySQL searches salary index

Step 2
Finds primary key = 5

Step 3
Uses primary key to fetch row from clustered index


------------------------------------------------------------


3. KEY DIFFERENCE

Feature              | Clustered Index | Non-Clustered Index
--------------------------------------------------------------
Storage              | Stores full row | Stores column + PK
Physical ordering    | Yes             | No
Number allowed       | Only one        | Multiple
MySQL name           | Primary Index   | Secondary Index


------------------------------------------------------------


4. IMPORTANT MYSQL BEHAVIOR

If a table has NO PRIMARY KEY:

MySQL will:

1) Use first UNIQUE NOT NULL index as clustered index

If that also does not exist

2) MySQL creates a hidden 6-byte row ID
   and uses it as clustered index.


------------------------------------------------------------


5. INTERVIEW ONE-LINE ANSWER

In MySQL InnoDB, the PRIMARY KEY acts as the clustered index
that stores actual table rows, while other indexes are
secondary indexes that store indexed columns along with
the primary key reference.

Produces and consumer problem

import java.util.LinkedList;
import java.util.Queue;

class SharedBuffer {
    private Queue<Integer> queue = new LinkedList<>();
    private int capacity = 5;

    public synchronized void produce(int value) throws InterruptedException {
        while (queue.size() == capacity) {
            wait(); // wait if full
        }

        queue.add(value);
        System.out.println("Produced: " + value);

        notify(); // notify consumer
    }

    public synchronized void consume() throws InterruptedException {
        while (queue.isEmpty()) {
            wait(); // wait if empty
        }

        int val = queue.poll();
        System.out.println("Consumed: " + val);

        notify(); // notify producer
    }
}


public class Main {
    public static void main(String[] args) {
        SharedBuffer buffer = new SharedBuffer();

        Thread producer = new Thread(() -> {
            int i = 0;
            while (true) {
                try {
                    buffer.produce(i++);
                } catch (InterruptedException e) {}
            }
        });

        Thread consumer = new Thread(() -> {
            while (true) {
                try {
                    buffer.consume();
                } catch (InterruptedException e) {}
            }
        });

        producer.start();
        consumer.start();
    }
}


# HashCode equals implementation when required
 
Suppose we create our own Employee class and want to insert objects into a Set based only on unique name (not reference):
-> We override hashCode() and equals()
-> In hashCode():   we generate hash based only on 'name'
-> In HashSet:   internally HashMap is used, and during add():
   existingKey.equals(newKey) is called
-> In equals():   
   1. Check reference (this == obj)
   2. Check type (instanceof)
   3. Compare name
-> If equals() returns true:  object is NOT inserted (duplicate)
-> Issue:   If 'name' is mutable and changed after insertion:
   hashCode changes → object may go to different bucket
-> This can lead to:   duplicate entry OR inability to find/remove object
-> Therefore:  fields used in hashCode/equals should be immutable (preferably final)

// SHALLOW COPY
// =======================
// New object, but internal references are shared

class Address {
    String city;
}

class User {
    String name;
    Address address;
}

User u1 = new User();
u1.name = "Tejas";
u1.address = new Address();
u1.address.city = "Pune";

// Shallow copy
User u2 = new User();
u2.name = u1.name;
u2.address = u1.address; // same reference

u2.address.city = "Mumbai";

// Effect:
// u1.address.city → "Mumbai" (changed)
// u2.address.city → "Mumbai"



// =======================
// DEEP COPY
// =======================
// New object + new nested objects (no shared reference)

User u3 = new User();
u3.name = u1.name;
u3.address = new Address();
u3.address.city = u1.address.city; // new object

u3.address.city = "Delhi";

// Effect:
// u1.address.city → "Mumbai" (unchanged)
// u3.address.city → "Delhi"

// =======================
// Copy used to protect internal state (encapsulation)

import java.util.*;

class Order {
    private List<String> items;

    // Constructor defensive copy
    public Order(List<String> items) {
        this.items = new ArrayList<>(items);
    }

    // Getter defensive copy

        return new ArrayList<>(items);
    }
}

Order order = new Order(list);

// order.items → ["Item1"] (safe, not affected)

@RestController
public class DemoRestController {

    private HashOperations<String, String, String> hashOps;
    private ListOperations<String, String> listOps;
    private SetOperations<String, String> setOps;

    public DemoRestController(RedisTemplate<String, String> rt) {
        this.hashOps = rt.opsForHash();
        this.listOps = rt.opsForList();
        this.setOps = rt.opsForSet();
    }

    // ---------- HASH ----------

    @PostMapping("/user")
    public String saveUser() {
        hashOps.put("USERS", "101", "Manish");
        return "User saved in HASH";
    }

    @GetMapping("/user")
    public String getUser() {
        return hashOps.get("USERS", "101");
    }

    // ---------- LIST ----------

    @PostMapping("/list")
    public String addToList() {
        listOps.rightPush("USER_LIST", "Manish");
        listOps.rightPush("USER_LIST", "Raj");
        return "Added to LIST";
    }

    @GetMapping("/list")
    public List<String> getList() {
        return listOps.range("USER_LIST", 0, -1);
    }

    // ---------- SET ----------

    @PostMapping("/set")
    public String addToSet() {
        setOps.add("USER_SET", "Manish");
        setOps.add("USER_SET", "Raj");
        setOps.add("USER_SET", "Manish"); // duplicate ignored
        return "Added to SET";
    }

    @GetMapping("/set")
    public Set<String> getSet() {
        return setOps.members("USER_SET");
    }
}

Saga design Pattern
===================

In a Choreography Saga, there is no central controller managing the transaction flow. Instead, each microservice reacts to events produced by other services. For example, when the Order Service creates an order, it publishes an OrderCreatedEvent to a message broker like Apache Kafka. The Payment Service listens to that event, processes the payment, and then publishes either a PaymentSuccessEvent or PaymentFailedEvent. Other services continue reacting to these events and performing their own local transactions. If a failure occurs, compensating events are published to undo previous actions, such as cancelling the order or releasing inventory. This approach creates very loose coupling because services only know about events, not about the entire workflow. It scales well and fits naturally into event-driven architectures. However, in large enterprise systems, choreography can become difficult to manage because event chains become complex, debugging is harder, and understanding the full transaction flow across services becomes challenging.


In an Orchestration Saga, the entire workflow is controlled by a central component called the Saga Orchestrator. Instead of services reacting independently to events, the orchestrator explicitly tells each service what action to perform. For example, the orchestrator first calls the Order Service to create the order, then calls the Payment Service to process payment, and then calls the Inventory Service to reserve stock. If any step fails, the orchestrator triggers compensating actions such as refunding the payment or cancelling the order. This provides much better visibility into the transaction lifecycle because the orchestrator maintains the current saga state, retry logic, timeout handling, and compensation flow in one place. Enterprise systems often prefer orchestration because production debugging, auditing, monitoring, and operational control become easier. Technologies like Temporal, Camunda, and Netflix Conductor are commonly used for orchestration-based saga implementations.


# Merge vs Rebase
================

## Initial State

```text id="jyb9dq"
main : A --- B --- C --- D

dev  : A --- B --- E --- F
```

---

# Merge

Command:

```bash id="97jvlm"
git merge main
```

Result:

```text id="krmxga"
A --- B --- C --- D
       \             \
        E --- F ------ M
```

* combines histories
* creates merge commit `M`
* original commits remain same
* safe for shared branches
* history becomes non-linear

---

# Rebase

Command:

```bash id="mjlwm6"
git rebase main
```

Result:

```text id="jlwm7q"
A --- B --- C --- D --- E' --- F'
```

* replays dev commits on top of latest main
* no merge commit
* linear clean history
* commit hashes change
* conflicts can occur while replaying commits

---

# Simple Difference

## Merge

```text id="8uq20j"
Combine histories
```

## Rebase

```text id="wljm9x"
Move my commits on top of latest branch
```

# Important Rule

```text id="jlwm8a"
Never rebase shared/public branches.
```


1) Why we need Refresh Token if we already have JWT Access Token
Access token is short-lived for security.
If stolen, attacker gets access only for limited time.
Refresh token helps generate new access token without forcing user to login again repeatedly.
2) Why not use only long-lived Refresh Token directly
Refresh token is not meant for API authorization.
Long-lived access token is dangerous if stolen.
Access token contains roles/permissions and is sent on every API request.
So access token is kept short-lived, while refresh token is used only occasionally to get new access token.
3) How Refresh Token verification works

Backend performs:

Verify token signature
Check token expiry
Extract userId/tokenId
Check Redis/DB to ensure token is active and not revoked
Load latest user roles/permissions
Generate new JWT access token
