Unit Testing for boot application
=================================

best practise (ask gpt for example) :
===============
Test your business logic, not framework code.
Keep one test focused on one behavior only.
Follow Arrange–Act–Assert consistently.
Use meaningful and descriptive test method names.
Prefer assertions on results or state over interaction verification.
Use interaction verification only when methods return void.
Avoid using times(1) unless call count actually matters.
Mock external dependencies, not your own classes.
Do not mock value objects, entities, or DTOs.
Write tests that are independent of execution order.
Avoid shared or static test data across tests.
Test both positive and negative scenarios.
Always test edge cases like null, empty, and invalid inputs.
Use assertThrows to verify exception behavior.
Keep unit tests fast and lightweight.
Do not load Spring context for unit tests.
Use constructor injection in production code to improve testability.
Avoid testing System.out.println or logging output.
Prefer returning values over void methods for better test assertions.
Use ArgumentCaptor when verifying transformed data.
Verify only what matters; avoid over-verification.
Ensure tests are readable without comments.
Avoid hard-coding unnecessary values.
Write tests that survive refactoring.
Code coverage is a metric, not a quality guarantee.
Remove redundant or duplicate tests.
Fail fast and fail clearly.
Keep assertions clear and specific.
Do not test private methods directly.
Treat unit tests as production-quality code.

Why exclusions exist (reality check)

You should exclude:

DTOs / POJOs
Config classes
Constants
Generated code
Main application class
Exception classes

You should NOT exclude:

Business logic
Services
Controllers (unless justified)

Jacoco measures coverage, not code quality. Excluding noise keeps reports honest.

Maven – Jacoco exclusions (MOST COMMON)
1️⃣ Add exclusions in jacoco-maven-plugin
<plugin>
    <groupId>org.jacoco</groupId>
    <artifactId>jacoco-maven-plugin</artifactId>
    <version>0.8.11</version>

    <configuration>
        <excludes>
            <exclude>**/dto/**</exclude>
            <exclude>**/config/**</exclude>
            <exclude>**/*Application.class</exclude>
            <exclude>**/exception/**</exclude>
        </excludes>
    </configuration>

    <executions>
        <execution>
            <goals>
                <goal>prepare-agent</goal>
            </goals>
        </execution>
        <execution>
            <id>report</id>
            <phase>test</phase>
            <goals>
                <goal>report</goal>
            </goals>
        </execution>
    </executions>
</plugin>

-@Test

Explanation: This annotation tells JUnit (a Java testing framework) that the method below is a test method.
It indicates that this method should be run as a test when using a test runner.
You must import it from org.junit.Test.

-assertEquals(expectedRes, actualRes);

Explanation: This is an assertion provided by JUnit.
It compares the expectedRes and actualRes. If they are equal, the test passes.
If they are not equal, the test fails, indicating a potential bug in the mul() method.

-@SpringBootTest

Explanation: This annotation tells Spring Boot to start the full application context for testing.
It’s useful when you want to test how different components work together, not just in isolation.
It loads all the beans like in a real application, so the test class behaves as if it's running inside the Spring Boot app.

-@ExtendWith(value = { MockitoExtension.class })

Explanation: This is a JUnit 5 annotation that tells the test to use Mockito’s features, like mock injections.
It's typically used in pure Mockito tests, but when you're using @SpringBootTest, this annotation may not be necessary unless you're doing hybrid mocking (can be omitted here).
However, it's not harmful and works for enabling Mockito annotations.

-@MockBean

@MockBean tells Spring to create a mock object of UserDao and inject it into the application context.
So when Spring initializes UserService (which depends on UserDao), it injects this mock instead of a real DAO implementation.
This is useful for unit testing the service layer without hitting the database.


-@InjectMocks

This tells Mockito to inject the mock dependencies (like userDao) into this UserService instance.
Since @SpringBootTest is also in use, Spring will usually handle this automatically, but it can act as a safeguard for manual setup.
This makes sure you're testing a UserService instance with a mocked UserDao.

1) Notes for testing with mockmvc json object :
----------------------------------------

In MockMvc testing, the HTTP response JSON is parsed into a tree structure, 
and we can access its data using jsonPath() starting from the root symbol $, as long as we know the field names or indexes.

JSON Response
{
  "id": 1,
  "name": "John",
  "email": "john@gmail.com"
}

Access using jsonPath

$ → root object
$.id → value of id
$.name → value of name
$.email → value of email

Example 2: JSON Array response
JSON Response
[
  { "id": 1, "name": "John" },
  { "id": 2, "name": "Smith" }
]

Access using jsonPath

$ → root array
$[0].id → id of first object
$[1].name → name of second object

2) testing xml:
------------
In MockMvc XML testing, responses are parsed into a DOM tree, and 
XPath is used to navigate and assert values starting from the root element using /.

| JSON Testing | XML Testing   |
| ------------ | ------------- |
| `jsonPath()` | `xpath()`     |
| `$` root     | `/` root      |
| Arrays       | Repeated tags |
| Key lookup   | Tag lookup    |

=> Conceptually:

JSON → parsed into JSON tree
XML → parsed into DOM tree
XPath navigates the XML tree

Test Method	Accept Header	Assertion
testGetCustomer_JSON()	application/json	jsonPath()

Same HTTP method, same URL, different tests.

4) Integration testing 
=> “Integration tests use SpringBootTest with real beans and DB, are executed by 
Maven Failsafe during the verify phase, and their coverage is visible in JaCoCo only 
when the report is generated after verify.”

Steps to Create Integration Tests (Spring Boot)
1️⃣ Create test class

Location: src/test/java
Naming must be:
*IT.java or
*IntegrationTest.java
Example:
CustomerControllerIT.java

2️⃣ Use correct annotations
@SpringBootTest
@AutoConfigureMockMvc
@Transactional
class CustomerControllerIT {
}

Why:
@SpringBootTest → loads full context
@AutoConfigureMockMvc → real HTTP calls
@Transactional → auto rollback after test

3️⃣ Do NOT mock internal layers
❌ No @MockBean for services/repos
Use real:
Controller
Service
Repository
DB (H2 / Testcontainers)

4️⃣ Use real DB (important)
Choose one:
H2 (quick)
Testcontainers (preferred in real projects)   -> coz we need db that behave same as prod db
Steps to Run Integration Tests
5️⃣ Add Failsafe plugin (mandatory)
<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-failsafe-plugin</artifactId>
  <executions>
    <execution>
      <goals>
        <goal>integration-test</goal>
        <goal>verify</goal>
      </goals>
    </execution>
  </executions>
</plugin>

6️⃣ Run correct Maven command

From IDE or terminal:
mvn clean verify
❌ mvn test → won’t run integration tests
Steps to See JaCoCo Integration Test Report
7️⃣ Add JaCoCo plugin (bound to verify)
Ensure report runs in verify phase
Ensure integration tests are included
(Without this → integration tests won’t appear)
8️⃣ Open correct report
After mvn verify, open:
target/site/jacoco/index.html

9️⃣ Verify execution
In console you must see:
Running CustomerControllerIT

If not seen → test never ran → no report.

========================
UNIT TEST ANNOTATIONS
========================

@Test
- Marks a method as a unit test.
- Used in all test types.

@ExtendWith(MockitoExtension.class)
- Enables Mockito WITHOUT Spring.
- Used for pure unit testing.
- No Spring context loaded.

@Mock
- Creates a mock object.
- Used to mock dependencies.

@InjectMocks
- Injects mocks into the class under test.
- Used for service / utility unit tests.

@WebMvcTest(Controller.class)
- Loads ONLY the controller layer.
- Does NOT load service, repo, DB.
- Used for controller unit testing.

@MockBean
- Creates a mock inside Spring context.
- Used with @WebMvcTest to mock service layer.

Example (Unit Test):

@ExtendWith(MockitoExtension.class)
class UserServiceTest {

    @Mock
    UserRepository repo;

    @InjectMocks
    UserService service;

    @Test
    void testLogic() {
        // unit test
    }
}

@WebMvcTest(UserController.class)
class UserControllerTest {

    @Autowired
    MockMvc mockMvc;

    @MockBean
    UserService service;
}



=============================
INTEGRATION TEST ANNOTATIONS
=============================

@SpringBootTest
- Loads FULL Spring Boot application context.
- Loads controllers, services, repos, configs.
- Used for integration testing.

@AutoConfigureMockMvc
- Enables MockMvc with real Spring context.
- Used for HTTP integration tests.

@Autowired
- Injects real Spring-managed beans.

@Transactional
- Rolls back DB changes AFTER each test.
- Keeps test DB clean.
- weather exception came or not, test completed or not data always rolled back if
  transactional is enabled
- only committed on success if we use @Commit 


@Commit
- Overrides rollback.
- Commits data even in tests.

@ActiveProfiles("test")
- Activates test-specific configuration.

Example (Integration Test):

@SpringBootTest
@AutoConfigureMockMvc
@ActiveProfiles("test")
@Transactional
class UserControllerIT {

    @Autowired
    MockMvc mockMvc;

    @Test
    void testEndToEndFlow() {
        // integration test
    }
}
