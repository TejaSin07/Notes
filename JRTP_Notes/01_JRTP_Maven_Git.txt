    - git add src/main/java

    - check current status (staged / unstaged / untracked files)

    - move staged files into the local repository as a commit

$ git branch -M main  
    - rename current branch to 'main' (force override if exists)

$ git remote add origin <repo-url>  
    - add remote repository URL and name it 'origin'

$ git push -u origin main  
    - push local commits to the remote repo and set upstream branch

$ git clone <repository-url>  
    - download a remote repository to local system (creates a new folder)

$ git restore <file>  
    - discard local changes in the working directory for that file  
      (to unstage: use 'git restore --staged <file>')

$ git log  
    - view commit history

$ git rm <file>  
    - remove file from working directory and stage the deletion  
      (must commit and push to reflect on remote)

$ git revert <commit-id>  
    - undo a commit by creating a new reverse commit  
      (must commit & push after revert)

$ git pull  
    - download changes from remote and merge into the current branch

Q. I created a new folder from scratch. How do I push my files to a remote repo ?
---------------------------------------------------------------------------------

Step 1: Go inside your project folder
cd /path/to/your-folder

Step 2: Initialize Git
Since this folder is brand new and not cloned:
git init

This creates a .git/ directory — now it’s a git repo.

Step 3: Add all files to staging
git add .

Step 4: Commit the files
git commit -m "Initial project commit"

Step 5: Add the remote repository URL
Replace <repo-url> with your GitHub/GitLab/Bitbucket repo URL:

git remote add origin <repo-url>


Example:

git remote add origin https://github.com/yourname/myrepo.git

Step 6: Push the files to the remote
If the remote branch is main:

git push -u origin main
If the remote uses master:

git push -u origin master
After this, future pushes are simple:

git push
✅ You’re done! Your scratch folder is now uploaded to the remote repo.
🔥 Why this works

Because you used:

git init → make the folder a git repo

git add → stage files

git commit → save snapshot

git remote add origin → connect to remote

git push → upload

1) git clone vs git pull

| Feature                 | `git clone`                 | `git pull`             |
| ----------------------- | --------------------------- | ---------------------- |
| Purpose                 | Get repo for the first time | Update existing repo   |
| Creates new folder?     | ✔ Yes                       | ❌ No                 |
| Downloads full history? | ✔ Yes                       | ✔ Only new changes    |
| Initializes `.git/`?    | ✔ Yes                       | ❌ Already exists     |
| Used once or repeated?  | Usually once                | Repeated many times    |
| Typical command         | `git clone <url>`           | `git pull origin main` |

2) git push vs git pull

| Feature                 | `git push`          | `git pull`               |
| ----------------------- | ------------------- | ------------------------ |
| Direction               | Local → Remote      | Remote → Local           |
| Purpose                 | Upload your commits | Download others’ commits |
| Requires local commits? | ✔ Yes               | ❌ No                   |
| Affects remote repo?    | ✔ Yes               | ❌ No                   |
| Affects local repo?     | ❌ No               | ✔ Yes                   |
| Typical use             | Share code          | Get latest code          |


3) git stash
	-> Suppose you pulled the latest code and started working on a specific file to fix Bug A. While you're partway through fixing Bug A (i.e., 
	your changes are not yet complete or committed), you're suddenly asked to prioritize and fix another bug (Bug B).

	To avoid losing your work on Bug A or committing incomplete code, you can use git stash to temporarily save your current changes.

	When you run git stash, Git stores all your uncommitted changes (staged and unstaged ) in a temporary memory area (called a "stash") 
	and restores your working directory to a clean state, just like it was right after your last pull.

	This allows you to switch context and fix Bug B without mixing it with incomplete changes from Bug A.

	Once Bug B is fixed and committed, you can return to your previous work by running git stash pop, which re-applies the saved changes from 
	Bug A so you can continue where you left off.

| Step | Command                    | Purpose                             |
| ---- | -------------------------- | ----------------------------------- |
| 1️⃣  | `git stash`                | Save (stash) current changes        |
| 2️⃣  | `git stash list`           | See all saved stashes               |
| 3️⃣  | `git stash show -p`        | Check what changes are inside stash |
| 4️⃣  | `git stash pop`            | Apply stash and remove it           |
| 5️⃣  | `git stash drop stash@{0}` | Delete specific stash manually      |



4) git fetch vs git pull

git rebase is used to move or replay your branch commits on top of another branch. It creates a clean, linear commit history by rewriting commit history.

GIT BASICS SUMMARY
==================

--------------------------------------------------
1) CREATION OF LOCAL REPOSITORY
--------------------------------------------------

Step 1: Create a project folder

    mkdir git-deep-practise
    cd git-deep-practise

Step 2: Initialize Git repository

    git init

What happens internally:

    .git/ directory is created

Structure:

    git-deep-practise/
        └── .git/
            ├── HEAD
            ├── config
            ├── objects/
            ├── refs/
            └── hooks/

Meaning of important folders:

    objects/    → stores commits, trees, blobs
    refs/       → stores branch pointers
    HEAD        → tells which branch is currently active
    config      → repo configuration

Example:

    cat .git/HEAD

Output:

    ref: refs/heads/main

Meaning:

    HEAD → main branch

--------------------------------------------------
2) CREATING BRANCH FROM MAIN
--------------------------------------------------

First check current branch:

    git branch

Example output:

    * main

Branches are stored in:

    .git/refs/heads/

Example:

    .git/refs/heads/main

Content:

    ad0a1ac316682dfd09d13ac4371a0d19653149ea

Meaning:

    branch name → commit hash

--------------------------------------------------

METHOD 1 : Create branch only

    git branch dev

Result:

    dev branch created but still on main

Check:

    git branch

Output:

      dev
    * main

--------------------------------------------------

METHOD 2 : Create branch and switch

    git checkout -b dev

Meaning:

    create branch + switch to it

--------------------------------------------------

METHOD 3 : Modern command (recommended)

    git switch -c dev

Meaning:

    same as checkout -b

--------------------------------------------------

Switch to existing branch:

    git checkout dev

or

    git switch dev

--------------------------------------------------

Branch pointer concept:

Before branch creation:

    main
     |
  commit A

After branch creation:

    main
     |
  commit A
     |
    dev

Both point to the SAME commit.

--------------------------------------------------
3) HOW HEAD WORKS
--------------------------------------------------

HEAD is a pointer that tells Git:

    "Which branch you are currently working on"

Check HEAD:

    cat .git/HEAD

Example output:

    ref: refs/heads/dev

Meaning:

    HEAD → dev

--------------------------------------------------

Switch branch example:

    git checkout dev

Internally Git changes:

    HEAD → refs/heads/dev

Working directory updates to dev snapshot.

--------------------------------------------------

Example state:

    main → commit A
    dev  → commit B

Graph:

        B (dev)
        |
        A (main)

HEAD → dev

--------------------------------------------------
4) WHAT HAPPENS WHEN COMMIT IS MADE
--------------------------------------------------

Example commit:

    git commit -m "Added dev feature"

New commit created:

    a3de8ac

Branch pointer moves forward.

Graph:

        a3de8ac  ← dev
           |
        ad0a1ac  ← main

Important rule:

    Commit moves the CURRENT branch only.

--------------------------------------------------
5) THREE IMPORTANT GIT AREAS
--------------------------------------------------

Git works with three areas:

1) Working Directory
2) Staging Area (Index)
3) Repository

Flow:

    Working Directory
            ↓
        git add
            ↓
      Staging Area
            ↓
        git commit
            ↓
         Repository

--------------------------------------------------
6) HOW FILES CHANGE WHEN SWITCHING BRANCH
--------------------------------------------------

Example:

main branch:

    app.txt → empty

dev branch:

    app.txt → "dev feature"

Switch branch:

    git checkout main

Result:

    Git restores files based on main commit snapshot.

Meaning:

    Working directory reflects the current branch state.

--------------------------------------------------
7) VISUAL FLOW
--------------------------------------------------

Initial:

    main
     |
  commit A

Create dev:

    main
     |
  commit A
     |
    dev

Commit in dev:

        commit B
           |
          dev
           |
        commit A
           |
          main

HEAD always points to current branch.

--------------------------------------------------
8) IMPORTANT INTERVIEW CONCEPT
--------------------------------------------------

A Git branch is NOT a folder.

A branch is simply:

    branch_name → commit_pointer

Example:

    main → ad0a1ac
    dev  → a3de8ac

Branch creation is extremely fast because:

    Git only creates a pointer, not a copy of files.
