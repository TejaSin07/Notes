6) | Feature               | PRIMARY KEY                      | UNIQUE                          |
| --------------------- | -------------------------------- | -------------------------------    |
| Purpose               | Uniquely identifies **each row** | Enforces uniqueness of a column    |
| NULL allowed          | ❌ **Not allowed**                | ✅ Allowed (DB-dependent)        |
| Number per table      | ❌ Only **one**                   | ✅ **Multiple** allowed          |
| Duplicate values      | ❌ Not allowed                    | ❌ Not allowed                   |
| Index created         | ✅ Yes (unique index)             | ✅ Yes (unique index)            |
| Can be composite      | ✅ Yes                            | ✅ Yes                           |
| Default identity      | ✅ Row identifier                 | ❌ Just a constraint             |
| Used for FK reference | ✅ Yes (recommended)              | ⚠️ Possible but not ideal       |

7) 

1. Constraint
   - A constraint is a RULE enforced by the database.
   - It protects data integrity.
   - It is stored in DB metadata, not in tables as data.

2. Constraint Type
   - Examples: UNIQUE, PRIMARY KEY, FOREIGN KEY, CHECK
   - These are predefined rule categories provided by DB.
   - We cannot create new constraint types.

3. Constraint Instance
   - A constraint instance is a specific rule applied to
     a specific table and column(s).
   - Every constraint instance belongs to ONE table only.

4. Named Constraint (explicit)
   - Example:
       CONSTRAINT uk_users_email UNIQUE (email)
   - Purpose:
       a) Give readable name to the rule
       b) Easy debugging (error messages)
       c) Easy ALTER / DROP later
   - Knowing the name avoids searching auto-generated names.

5. Unnamed Constraint (implicit)
   - Example:
       email VARCHAR(100) UNIQUE
   - DB still creates a constraint instance internally.
   - Name is auto-generated by DB.

6. UNIQUE constraint behavior
   - Ensures no duplicate values in the same table.
   - Applies only to the table where it is defined.
   - Each table gets its own UNIQUE constraint instance.

7. Why UNIQUE looks reusable
   - UNIQUE keyword can be used in any table.
   - But every usage creates a NEW constraint instance.
   - Instances are NOT shared across tables.

8. FOREIGN KEY constraint behavior
   - Ensures value exists in another table.
   - Enforces relationship between tables.
   - Also creates a table-specific constraint instance.

9. Important truth
   - Constraint TYPE is reusable (keyword).
   - Constraint INSTANCE is NOT reusable.
   - Constraint INSTANCE is always table-scoped.


NOTE::
Column-level rules → stored in column metadata (NOT NULL)
Uniqueness rules  → stored as indexes (UNIQUE, PK)
Relationship rules → stored as constraints (FOREIGN KEY)

SCENARIO: Updating a PRIMARY KEY referenced by a FOREIGN KEY

Parent table: users
Child table : user_profile (FK owner)


CASE 1: No ON UPDATE CASCADE (default behavior)

UPDATE users SET user_id = 10 WHERE user_id = 1;

Result:
❌ ERROR – Database blocks the update

Reason:
- user_profile.user_id references users.user_id
- Updating PK breaks referential integrity
- DB prevents it by default


CASE 2: With ON UPDATE CASCADE

FOREIGN KEY (user_id)
REFERENCES users(user_id)
ON DELETE CASCADE
ON UPDATE CASCADE;

UPDATE users SET user_id = 10 WHERE user_id = 1;

Result:
✅ SUCCESS
- users.user_id updated (1 → 10)
- user_profile.user_id auto-updated (1 → 10)


KEY RULES:
- Primary keys should be IMMUTABLE
- Updating PK is bad design in most systems
- Prefer AUTO_INCREMENT / UUID PKs
- Update business fields, not PKs


INTERVIEW LINE:
"Updating a primary key usually indicates a flawed data model."

ONE to ONE imp point ::
------------------------

1. Decide the owner table
   - The table that holds the FOREIGN KEY is the owner
   - Ownership must be single and clear

2. Foreign key column is REQUIRED
   - Child table must contain FK referencing parent PK

3. FOREIGN KEY constraint must be defined
   - Enforces referential integrity
   - Prevents invalid references

4. UNIQUE constraint on the foreign key  (IMP)
   - This is what enforces ONE-TO-ONE
   - Without UNIQUE → relationship becomes ONE-TO-MANY

5. Decide NULL vs NOT NULL on FK
   - NOT NULL → mandatory relationship
   - NULL     → optional relationship

6. Define delete behavior explicitly
   - ON DELETE CASCADE  → child auto-deleted
   - ON DELETE RESTRICT → prevents parent delete
   - Never rely on default behavior

7. Use stable PRIMARY KEY in parent
   - Prefer AUTO_INCREMENT / UUID
   - Never update PK

8. Index the foreign key column
   - Improves join and delete performance
   - Often auto-created, but must be ensured



One to Many:
------------

In a one-to-many relationship, orders are fetched using the foreign key on the many side, 
typically via a JOIN between parent and child tables.

Many to many :
--------------

A many-to-many relationship is implemented using a junction table with foreign keys to both parent tables and a composite primary key to prevent duplicate associations.

1. Junction table is REQUIRED
2. Junction table contains ONLY FKs (plus extra columns if needed)
3. Composite PRIMARY KEY prevents duplicates
4. FK constraints enforce integrity
5. ON DELETE CASCADE cleans mappings automatically
